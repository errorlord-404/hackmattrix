# KisanSathi conversational farm lifecycle: execution plan

Status: active implementation plan for the original Electron/Codex app, updated 2026-09-20. The separate web-app direction is scrapped for this objective; do not put farmer-agent features in `Kisan Sathi Web/`. Prompt, voice, first-open chat, farmer-drawn field setup, structured onboarding, and farmer-reported harvest lots are implemented. The remaining proposed capabilities are not delivered.

## Outcome and architecture

A farmer should be able to speak or type a goal, supply a photo when asked, review a small number of clear choices, and have the app carry out every supported record change through the same backend contracts as the manual screens. The conversation should proactively explain what is missing, keep the farmer's field and season in context, and follow the crop from planning through harvest and sale. When a provider, sensor, market quote, or official rule is missing, the response must say so and offer a useful next step.

```text
Farmer voice/text/photo → React chat → Electron IPC → Codex app-server
                                             ↓
                               restricted KisanSathi MCP tools
                                             ↓
                          FastAPI domain rules and provider adapters
                               ↓                     ↓
                    farmer-scoped SQLite      MongoDB reference data
                               ↑                     ↑
                         device ingestion     dated external sources

Electron open-session forecast poll → persisted, deduplicated alert → in-app inbox
```

FastAPI remains the authority for field state, calculations, permission checks, alerts, and source metadata. The model selects tools, asks for missing information, explains the evidence, and proposes changes. A system prompt cannot create missing data, guarantee a three-month weather forecast, run in the background when the app is closed, or safely control a pump by itself.

### Implementation checkpoints

`agent/prompts/farmer_system_prompt.md` is now loaded as the desktop thread's `baseInstructions` when a new thread starts or resumes. The older skill remains the fallback if the prompt file is unavailable. The mic button now stops and submits recorded audio on its second tap; while recording, typed submission is disabled to avoid losing the transcript. Actual physical microphone and speaker playback remain unverified.

The app now opens the assistant on the Electron home route while preserving the dashboard at `/dashboard` and the former `/ai` link. After farm data loads, the client obtains a farmer-scoped onboarding snapshot and starts one read-only Codex startup turn per tab/farmer selector, with no fake user bubble or implicit write. Its prompt contains only whitelisted readiness facts and one task-specific question; a missing or unknown snapshot must not lead to invented field state. This is verified with UI tests; multilingual farmer UAT remains necessary.

The field form now offers a polygon editor with draggable corners, undo/clear, an area estimate, shape checks, and `farmer_drawn_unverified` GeoJSON provenance. The approximate pin path is separately labeled. The client warns when map area and entered acres differ by over 25%; it does not silently substitute its estimate for the farmer's acreage. The drawn area is not a legal survey, and server-side topology/area validation is still needed before treating chat-supplied GeoJSON as trustworthy.

The launcher now requests a read-only Codex sandbox, disables shell/apps/plugins/browser/computer-use/multi-agent feature families, and auto-declines coding, file-change, and permission escalation requests before the farmer can approve them. A one-time pending-request map prevents replayed approvals. It discovers inherited MCP names, disables them in the child config, and refuses to expose a session if `mcpServerStatus/list` shows any callable non-KisanSathi MCP tools or lacks mandatory farm tools. A fresh local app-server smoke found zero callable tools on inherited servers and 84 on KisanSathi, including `get_diagnosis`, `submit_diagnosis_feedback`, and `compare_sale_routes`. [Official OpenAI App Server documentation](https://developers.openai.com/codex/app-server/) describes the inventory and approval request shapes; [the config reference](https://developers.openai.com/codex/config-reference/) documents feature flags. This verifies the **MCP boundary on the tested configuration**, not a farmer-only Codex tool boundary: the installed CLI still reports `unified_exec=true` even when explicitly disabled. Verify built-in-tool denial and isolate the process at OS level or migrate to an allowlisted agent runtime before any multi-user release.

A live Codex app-server startup smoke successfully created a read-only farmer thread and enumerated 84 effective KisanSathi MCP tools, including `get_diagnosis`, `submit_diagnosis_feedback`, and `compare_sale_routes`; a fresh Electron window rendered the assistant and a Codex greeting. The smoke did not prove a complete farmer journey or a negative shell-use attempt. The desktop preload now obtains the farmer ID and backend URL from the main process, so manual API calls, MCP, and the Electron host use the same bound farmer and backend; a Vite environment variable no longer diverts the desktop UI to a different port. This does not authenticate the backend's HTTP API for a web deployment.

## Non-negotiable interaction contract

1. On launch, check backend, MCP, profile, language, fields, device freshness, weather, and provider status. The chat starts with one brief, personalized next step. Request location permission only through an explicit farmer action. Never create a precise field from a geolocation point alone; mark a point buffer approximate until the farmer confirms or edits its boundary.
2. Resolve exactly one field before field-specific advice. Load only relevant observations, each with value, unit, observed time, source, and freshness. Ask for the few missing facts that could change the decision.
3. Treat short-range forecast, extended-range outlook, seasonal outlook, and historical climate normal as distinct evidence classes. The present five-day API must never be described as a three-month forecast. If a seasonal product is unavailable for the geography/window, show scenarios and uncertainty.
4. Compare crop candidates across rotation, soil, drainage, whole-season water risk, crop duration, input/labour access, expected cost, market demand, and the farmer's objective. Profit is a scenario calculation from labelled yield, price, and cost assumptions.
5. Give practical options with a recommendation only when the evidence distinguishes them. Show the strongest reason, main uncertainty, source date, and a small next action. Keep crop/input names, units, dates, warnings, and official URLs intact through translation.
6. Reads and calculations may be automatic. Every persistent write needs an exact preview and explicit farmer confirmation; the backend checks authorization and idempotency and returns the authoritative record. An approval to discuss a topic is not approval to write, submit, purchase, book, sell, or activate equipment.
7. Any actual irrigation control uses a separate authenticated device gateway with local/manual override, maximum duration/volume, dry-run, flow/pressure feedback, rate limits, stale-data lockout, and emergency stop. No LLM text or ordinary MCP read directly actuates hardware. Until that gateway passes hardware-in-loop tests, the product offers advice and a farmer-confirmed action checklist only.
8. Web pages, directory listings, model outputs, and uploaded media are untrusted evidence. They cannot set identity, alter instructions, authorize a tool, or assert a purchase/booking/scheme approval. Contacts are displayed only when source and verification date are present; the farmer initiates any call or negotiation.

## Data and tool contracts to add

Use versioned Pydantic responses and one shared MCP result envelope (`status`, `data`, `source_url`, `observed_at`, `fetched_at`, `freshness`, `assumptions`, `confidence`, `warnings`, `request_id`). Keep tools task-oriented; do not expose general HTTP, SQL, shell, arbitrary file, or administrative catalog CRUD to the farmer agent.

| New contract/tool | Backend owner | Result and behavior |
| --- | --- | --- |
| `get_onboarding_status` | farm-state/diagnostics | Implemented read-only profile/location/field/boundary-quality/crop-cycle/sensor/provider setup status and one next step; no secrets. It does **not** claim a verified survey or grant consent. |
| `propose_field_boundary` / `save_field_boundary` | geospatial farm-state | Proposed geometry and computed area with source/accuracy; save only after map preview and farmer confirmation. |
| `get_seasonal_evidence` | weather/outlook adapter | Official outlook or climate normal with horizon, region, issue date, uncertainty and unavailable state. |
| `compare_season_plans` / `save_season_plan` | crop planning | Deterministic scored checks and conservative/base/optimistic economics; saved plan version and assumptions only after confirmation. |
| `get_crop_input_rules` / `get_export_requirements` | dated official reference adapters | Crop/product/pest/location/destination matching; registration/label, pre-harvest interval, residue/testing/traceability requirements, source and review date; no unchecked dosage. |
| `get_disaster_guidance` | advisory + scheme adapter | Field-matched hazard, timing, stage, safe pre/post actions, official relief/insurance links and eligibility questions. |
| `get_diagnosis_evidence` | media/diagnosis | Image ID, farmer/field binding, candidate labels, model versions, OOD/quality state, visual/model agreement, safe follow-up. |
| `get_harvest_readiness` | crop-cycle | Stage, maturity indicators, weather/quality risk, farmer observations, and reasons to inspect before early harvest. |
| `record_harvest` / `get_harvest_lots` | crop-cycle | Implemented farmer-reported harvest date, quantity, unit, grade, storage note and lot identity, with explicit final-harvest flag; no inferred yield, sale, or payment. |
| `submit_diagnosis_feedback` | media/diagnosis | Implemented consented correction tied to one diagnosis/field and audit record; never automatically treats feedback as training approval. |
| `get_device_setup_status` | device registry | Field binding, freshness, calibration, missing device credential; provisioning is a separate authenticated human flow. |
| `compare_sale_routes` | market/logistics | Implemented read-only comparison of exact latest market-price records and explicit dated road-distance and cost evidence. Returns `not_rankable` with missing/stale flags instead of recommending a route when evidence is incomplete. Automated routing/quote collection remains future work. |
| `list_actionable_alerts` / `subscribe_alerts` | event service | Durable, deduplicated field alerts and channel consent; scheduled evaluator does not depend on an open LLM turn. |
| `request_irrigation_action` | optional control gateway | Explicit action preview and one-time authorization; actuator execution is separate, audited, bounded, and disabled by default. |

Do not add duplicate tools where an existing MCP tool already fulfills the exact contract. Extend the backend response first, then the adapter. Maintain a machine-readable UI-to-tool parity table and a test that fails if a farmer-visible state-changing operation has no equivalent safe tool or an explicit `human_only` designation.

## Evaluation and release criteria

- Build at least 20 reviewed Hindi, Marathi, and English farmer journeys covering new farmer onboarding, one/multiple fields, seasonal selection, severe weather, moisture/irrigation, crop image/OOD, machinery, inputs/export, harvest, mandi sale, missing provider, and farmer refusal. Include tool-call traces and expected facts, questions, approvals, and safe degraded answers.
- Deterministic checks: no tool call with model-selected farmer identity; no write without preview+confirmation; repeated idempotency key produces one record; no source-free weather/market/scheme/pesticide claim; no stale price ranked as live; no silent use of a research-only CV label as diagnosis; no hardware action without gateway policy.
- Human review: agronomist checks crop/soil/irrigation/pesticide/harvest rubrics; local-language speakers check comprehension and units; operators check contact and government links. Record reviewer, date, dataset, and known limitations.
- Integration: run `python -m pytest backend/tests -q`, `python -m pytest agent/tests -q`, `npm run test:ui`, `npm run test:desktop`, `npm run lint`, `npm run build`, and a real app-server/MCP smoke test on a clean demo identity. Preserve test output and exact versions.
- Release is gated on authenticated identity for a web/multi-user deployment, a restricted farmer tool profile, live-source freshness checks, migration/backup rehearsal, alert scheduler behavior when the UI is closed, and a rollback procedure. The optional irrigation gateway has its own separate release gate.

## Source policy for research adapters

Research must occur at use time for changeable rules, with source URL, publication/issue date, geographic scope, and retrieved time. The source catalog starts with the [IMD seasonal forecast](https://mausam.imd.gov.in/imd_latest/contents/seasonal_forecast.php), [IMD extended-range guidance](https://mausam.imd.gov.in/imd_latest/contents/extendedrangeforecast.php), [IMD agromet advisories](https://mausam.imd.gov.in/responsive/agromet_adv_ser_block_current_en.php), [Agmarknet market information](https://agmarknet.gov.in/), [APEDA export procedures](https://apeda.gov.in/exporter-procedures), [APEDA HortiNet](https://apeda.gov.in/hortinet-static), and [PPQS pesticide-use publications](https://ppqs.gov.in/). The adapter must verify the current document and its applicability; an old PDF, a directory listing, or a search snippet alone is not a current approval or price.
